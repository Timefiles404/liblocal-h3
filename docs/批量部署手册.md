# 批量部署手册

面向「多台 Windows 机器」的部署流程。首台（CHINAMI-1，RTX 5080）已实跑并回填，
所有已知坑都已修进脚本。**第一台会暴露问题，后续机器应当一次通过。**

---

## 一句话流程

```powershell
# 第 1 步：拿代码（走 GitHub，大陆可能需要代理）
git clone --depth 1 https://github.com/Timefiles404/liblocal-h3.git D:\Liblocal

# 第 2 步：装运行时（会装 uv/Python/ComfyUI/torch，并把镜像批权重挂后台下载）
powershell -NoProfile -ExecutionPolicy Bypass -File D:\Liblocal\deploy\setup.ps1 -InstallDir D:\Liblocal
```

之后等镜像批（约 33GB）下完，再单独跑一次超分权重：

```powershell
# 第 3 步：超分权重（约 90MB，github 批）
powershell -NoProfile -ExecutionPolicy Bypass -File D:\Liblocal\deploy\get-models.ps1 -Batch github
```

---

## 权重分两批下载（重要）

部署的流量天然分两类，**代理策略相反**，混在一起会明显变慢：

| 批次 | 内容 | 大小 | 网络策略 |
|---|---|---|---|
| `mirror` | H3 主权重（魔搭） | 约 33GB | **必须直连**，走代理又慢又费流量 |
| `github` | 超分权重（hf-mirror / GitHub Releases） | 约 90MB | 大陆常需代理；脚本会自动选路并带国内加速兜底 |

这样拆开的好处：33GB 那批可以放着慢慢下、不需要代理；90MB 那批**开着代理几分钟就完事**。
脚本自己也按批处理代理——`get-models.ps1` 在 mirror 批里会显式清空 `HTTPS_PROXY`，
不会因为环境里残留代理而走错路。

```powershell
# 只跑某一批
.\deploy\get-models.ps1 -Batch mirror     # 关代理跑
.\deploy\get-models.ps1 -Batch github     # 开代理跑（或直连，脚本自己选）

# 一批跑完再跑另一批（推荐，便于分别控制代理）
# 也可以一次跑完两批（注意此时代理状态对两批的影响）
.\deploy\get-models.ps1 -Batch all
```

完成戳写在 `data\state\models-<batch>.stamp`，内容 `OK` 或 `FAILED ...`。
**判断完成请看戳，不要 grep 日志里的 `DONE`** —— 日志会轮转，但戳不会骗人。

## 前端来自我们的 fork（不再打补丁）

PinCanvas 上游已停更（最后提交 2026-05-29）。我们 fork 到
**`Timefiles404/PinCanvas`** 的 **`liblocal`** 分支，本地改造直接提交在里面：

```powershell
git clone --depth 1 --branch liblocal https://github.com/Timefiles404/PinCanvas.git
```

`setup.ps1` 会自动做这件事，所以部署时**不需要打补丁**。

> **为什么不再用补丁**：早先的方案是「克隆上游 7419da0 + 应用 pincanvas-local.patch」，
> 但补丁很脆——行尾、空白、上游任何变动都会让它 `corrupt patch` 或 apply 失败，
> 而且失败时如果 dist 已经存在，跳过逻辑还会把问题永久掩盖。fork 分支一次搞定，
> 也便于后续继续加功能（超分节点就是这么加的）。

`.npmrc` 已指向 npmmirror，`npm install` 不会去连官方源，也不会改用户的全局 npm 配置。

## 网络分阶段策略（重要）

部署天然分成两段，代理策略相反，混用会明显变慢甚至失败：

| 阶段 | 目标站点 | 策略 |
|---|---|---|
| **A. GitHub 侧** | github.com（git / uv / CPython / ComfyUI / PinCanvas / winget 装 git） | 大陆直连偏慢或不通，**需要代理** |
| **B. 国内镜像侧** | 魔搭权重 36GB、清华 PyPI、阿里云 torch、npmmirror | **必须直连**，走代理既慢又白烧流量 |

脚本已按此分阶段处理：

- `setup.ps1` 在离开 GitHub 阶段后**自动清除 git 全局代理**（`http.proxy`/`https.proxy`）。
  这个配置是持久的，进程内清环境变量清不掉——不清掉的话后面 36GB 魔搭流量会误走代理。
- `bootstrap.ps1` 只在克隆时用 `git -c http.proxy=...` 注入**本次命令**的代理，
  不写全局配置，从根上避免残留。

## 超分辨率

H3 的生成画布上限约 768×1344（模型训练范围）。再往上属于**像素级放大**，
不靠重新生成，而是走后处理 —— 这条路线参考了 h3lite 的 `references/video-upscale.md`。

画布上有一个独立的**超分辨率节点**（`upscale`），也可直接调 API：

```powershell
# 端到端：把一张产出图放大 2x
curl -X POST http://127.0.0.1:8801/api/upscale `
  -H "Content-Type: application/json" `
  -d '{"image":"image_00001_.png","subfolder":"liblocal","method":"esrgan","scale":2}'
```

| 方式 | 说明 | 需要权重 |
|---|---|---|
| `esrgan`（默认） | 4x 模型超采样，再 Lanczos 降采样到目标倍数。**2x 是「4x 再缩」而不是直接 2x**，比直接放大更锐 | 是 |
| `lanczos` | 纯几何缩放 + 轻度锐化，无模型推理 | 否（自动回退） |

`scale` 可填 `1.5 / 2 / 3 / 4`。4 是模型原生倍数，也最快（不用二次重采样）。

**超分是独立端点、独立队列任务**，不是生成图里的一个开关 —— 这样超分失败
（比如大图 OOM）不会让一次已经成功的生成作废。

超分权重清单：

| 文件 | 大小 | 来源 | 说明 |
|---|---|---|---|
| `4x-UltraSharp.pth` | 66,961,958 B | hf-mirror（Kim2091/UltraSharp） | 通用 4x，质量/体积平衡最好，**默认** |
| `RealESRGAN_x4plus.pth` | 67,040,989 B | GitHub Releases（xinntao/Real-ESRGAN） | 写实照片风格稳 |
| `RealESRGAN_x4plus_anime_6B.pth` | 17,938,799 B | 同上（v0.2.2.4） | 动漫/插画风格 |

`4x-UltraSharp` 有 sha256 校验（`a5812231...21fe01`），下载器会核对，
因为历史上出现过 0 字节占位文件冒充权重的情况。

**不装超分权重也能用**：`doctor.py` 会提示「回退到 Lanczos」，功能不缺失，只是效果差一些。

### 关于视频超分

视频超分**不做成独立端点**，因为「读一个 mp4 → 逐帧超分 → 重新封装」在
stock ComfyUI 里没有干净的输入路径（`LoadVideo` 不产出 IMAGE batch）。
可行且已有的做法是把超分**融合进生成图**：H3 解码出来的帧批次直接接超分节点，
再 `CreateVideo` 封装，音频沿用 H3 已解码的那路
（编排器里是 `upscale.build_video_upscale_inline`，接收上游的 `frames_ref` 与 `audio_ref`）。

外部工具路线（Topaz Video AI / FlashVSR）**故意没有接入**：前者要授权，
后者要独立 Python 环境和约 7GB 权重包，都会破坏「解压即用」这个前提。
需要的人可以直接照 h3lite 的文档手动跑，那篇文档把两者的显存分档、tile 陷阱
（`--tile_size 128 --tile_overlap 24` 是唯一会出网格的参数组合）、音频需要单独
从源视频回封等都写得很清楚。

## 已知坑与处置（首台实测记录）

### 1. 无 BOM 的 .ps1 在中文系统上整份解析崩溃

**现象**：`powershell -File setup.ps1` 报一屏语法错（`Unexpected token '}'`、
`The '<' operator is reserved for future use`），定位到中文注释附近。

**根因**：PS 5.1 读**无 BOM** 的 .ps1 时按系统 ANSI（中文=GBK）解码。中文注释变成
乱码字节，其中恰好可能构成 `"` `<` `}` 等语法字符 → 解析彻底崩坏。

**已修**：`deploy/*.ps1` 全部加 UTF-8 BOM，`.gitattributes` 里用 `*.ps1 -text`
禁止 git 改字节。

**为什么值得记住**：这个坑极其隐蔽——脚本在 UTF-8 环境（如本机 pwsh 7）完全正常，
只在目标机的 PS 5.1 + 中文 locale 下爆。**新增任何 .ps1 都必须带 BOM。**

### 2. `$ErrorActionPreference='Stop'` 被原生命令的 stderr 误触发

**现象**：跑到「安装 ComfyUI 依赖」时，uv 刚打印一行
`Using Python 3.12.14 environment at: ...` 就抛 `NativeCommandError` 终止。

**根因**：PS 5.1 下 `& native.exe 2>&1 | ...` 会把原生命令写到 stderr 的**任何**
进度行包装成 ErrorRecord；配合 EAP=Stop 直接当终止性错误。uv/git/npm 都会往
stderr 写正常进度。

**已修**：脚本改用 `$ErrorActionPreference='Continue'`，真正的失败由 `Die()` 抛异常、
以及显式检查 `$LASTEXITCODE` / 文件是否存在来判定。

### 3. PyTorch 镜像：必须逐版本核对 cp312 + win_amd64

**现象**：官方源 `download.pytorch.org` 大陆直连极慢（1.9GB 的 torch 拖到无法接受）。

**踩坑过程**：
- NJU `mirrors.nju.edu.cn/pytorch/whl/cu130/` 是 PEP503 结构（能当 `--index-url`），
  但 cu130 下**只有 cp313/cp314/cp315，没有 cp312** → 不可用（本机 venv 是 3.12）。
- SJTU 同样缺 cp312 win_amd64。
- 阿里云 `mirrors.aliyun.com/pytorch-wheels/cu130/` **有完整 cp312 win_amd64**，
  但它是**平铺目录**（根页直接列全部 .whl，无 `torch/` 子目录）→ **不是 PEP503，
  不能当 `--index-url`**，必须用 `--find-links`。

**三件套版本强绑定**：cu130 下 torchaudio 最高只到 2.11.0，而 torch 能到 2.14；
写裸包名会解析出不配套的组合。必须写死：
`torch==2.11.0+cu130 torchvision==0.26.0+cu130 torchaudio==2.11.0+cu130`

**已修**：`setup.ps1` 用
`--index-url https://pypi.tuna.tsinghua.edu.cn/simple --find-links https://mirrors.aliyun.com/pytorch-wheels/cu130/`
配上述三个精确版本。

### 4. `modelscope` 的调用方式（最阴险的静默失败）

**现象**：5 个权重各 1 秒失败，日志尾部却出现 `完成但有失败 + DONE`，
而 `setup.ps1` **返回成功**（下载是独立后台进程，状态不回传）。

**根因**：modelscope 1.40.0 已移除 `python -m modelscope` 入口：
`No module named modelscope.__main__`。正确入口是 `modelscope.exe` CLI，
参数是**位置式**的：`modelscope download <repo> <file> --local-dir <dir>`
（注意是 `--local-dir` 带连字符；没有 `--model`）。

**已修**：模板改为定位并调用 `modelscope.exe`；找不到就明确报错并计入失败列表。

**同时加了两道防线**：
- **首文件哨兵**：启动下载后等 45 秒，若既没有文件落地也没有进度输出，
  就在 `setup.ps1` 里明确告警（而不是默认成功）。
- **完成戳**：`data\state\models-download.stamp`，内容 `OK` 或 `FAILED ...`。
  外部只认这个戳，不要去 grep 日志文本。

### 5. 追加式日志导致完成判断误触

**现象**：用日志里的 `DONE` 作为完成信号，结果误触——那个 `DONE` 是上一次失败运行留下的，
日志是追加的。

**已修**：每次启动下载前**轮转**日志（改名带时间戳），并清掉旧完成戳。
完成判定只看 `models-download.stamp`。

### 6. 前端补丁损坏 + 跳过逻辑掩盖问题

**现象 A**：`git apply` 报 `corrupt patch at ...:96`，共 7 处。

**根因**：生成补丁时用了 `git diff ... 2>&1 > file`，把 git 的 stderr
（`warning: in the working copy of 'x', LF will be replaced by CRLF...`）
混进了补丁文件，其中 4 段**内嵌把代码行劈成两半**。

**已修**：重新生成补丁（不重定向 stderr，`core.autocrlf=false`），
并在**干净的 7419da0 副本**上验证 `git apply --check` 通过、应用后内容与源逐字节一致。

**现象 B**：第一次补丁失败但构建成功（dist 有产物）；再跑脚本时看到
`dist/index.html` 存在就**整段跳过**，补丁永远补不上。

**已修**：跳过条件改为看 `.liblocal-patched` 戳；戳不在就重打补丁并清 dist 重建。

**发布前必须做**：`git apply --check` 是硬门禁。补丁用 `git diff` 生成时
确保 `core.autocrlf=false` 且不混入 stderr。

### 7. npm / Node 小坑

- `npm install` 默认源慢 → 脚本在 `PinCanvas\.npmrc` 写 `registry.npmmirror.com`
  （**不要**改用户的全局 npm 配置）。
- `npm warn EBADENGINE`（eslint-visitor-keys 要求 node ^20.19.0，本机 v20.18.1）
  → 构建仍成功，但建议装 Node 20.19+ 或 22 LTS 消除警告。

### 8. 机器寻址（工具使用细节）

Vantaloom 里本机的 machine id 是 `local`，主机名是 `CHINAMI-JSJG39U`。
用 `machine://CHINAMI/...` 寻址会报「未配置」。批量对接时统一维护
「机器 id ↔ 主机名」对应表，不要手写 id。

# 1) 自检（硬件/模型/端口/启动参数）
